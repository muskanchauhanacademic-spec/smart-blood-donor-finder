## 1. The 30-second summary

Our app has patients who need blood and donors who can give it. My part turns this into a **graph**: every patient and every donor is a dot, and a line joins a patient to a donor when that donor can help that patient (blood group compatible, donor available, and the city matches if a city filter is on).

I store the graph as a **table of 0s and 1s** (the adjacency matrix): rows are patients, columns are donors. Adding up a row tells us how many donors can help that patient. Adding up a column tells us how many patients that donor could serve. These counts are called **degrees**.

The project needs this because the matching algorithm (Dev 4) works on my table, and the graph pages (Dev 5) draw my lines.

## 4. Algorithms and key ideas

### 4.1 The bipartite graph and the edge rule

**Idea in plain English.** Think of a school dance where boys stand on the left and girls on the right, and we only draw a line between a boy and a girl who *want* to dance together. There are never lines between two boys. That is a **bipartite graph** ("two parts"). Ours: patients on the left (set P), donors on the right (set D), written **G = (P ∪ D, E)** where E is the set of edges (lines).

An edge between patient *i* and donor *j* exists exactly when `compat_is_edge` says yes, which means all three are true:
1. the donor's blood group can be given to the patient's blood group (27 of the 64 possible combinations are compatible),
2. the donor is available,
3. the donor's city matches the city filter (or there is no filter).

My code **never re-implements** this rule. One rule in one place (Dev 2's `compat_is_edge`) means the search page, graph and matching can never disagree.

**Why all patients stay when a city filter is on.** The set P is *all patients*, always. A filter only decides which *lines* exist (it looks at the donor's city). A patient with no line is still a patient; it shows up with degree 0, which tells the user "no donor found for this patient in that city". If I deleted such patients, the user could not see who is unserved.

**Worked example (3 patients, 3 donors).** Patient ids 1, 2, 3; donor ids 101, 102, 103.

```
   Patients (rows)                  Donors (columns)

   P1 (id 1) ----------------------- D1 (id 101)
   P1 (id 1) ----------------------- D2 (id 102)
   P2 (id 2) ----------------------- D1 (id 101)
   P3 (id 3) ----------------------- D2 (id 102)
   P3 (id 3) ----------------------- D3 (id 103)

   5 edges.  No line joins two patients or two donors.
```

As an adjacency matrix (row = patient, column = donor):

```
              D1(101) D2(102) D3(103)
   P1 (id 1)     1       1       0       row sum = 2
   P2 (id 2)     1       0       0       row sum = 1
   P3 (id 3)     0       1       1       row sum = 2
   column sum:   2       2       1       total = 5
```

In C and JSON this is `[[1,1,0],[1,0,0],[0,1,1]]`.

**Pseudocode.**
```
for each patient row i:
    for each donor column j:
        if compat_is_edge(donor j, patient i, cityFilter): adj[i][j] = 1, edgeCount++
```

**Real code excerpt** (`graph_build`):
```c
for (i = 0; i < n; i++) {
    for (j = 0; j < m; j++) {
        if (compat_is_edge(&store->donors.items[j],
                           &store->patients.items[i],
                           g->cityFilter)) {
            if (g->edgeCount == INT_MAX) {   /* cannot count higher */
                st = STATUS_ERR_INTERNAL;
                goto fail;
            }
            g->adj[i][j] = 1;
            g->edgeCount++;
        }
    }
}
```

**Cost.** Time: n x m calls to `compat_is_edge` (each one is a small, fixed amount of work per the spec: a table lookup and a short city comparison). Memory: n x m numbers.

**Why this approach / alternative.** One simple double loop that a beginner can read, and it reuses the single edge rule. *Alternative:* build only the list of edges (an edge list or adjacency list). That uses less memory for sparse graphs, but our graph is expected to be dense (see 4.2).

### 4.2 The dynamic adjacency matrix (`int **adj`)

**Idea in plain English.** The number of patients and donors is not known when we compile, and the project forbids fixed limits. So the table must be created **while the program runs**. In C a table of unknown size is built in two steps: first an array of *row pointers*, then one row of numbers for each pointer.

```
 adj ----> [ ptr0 ] ----> [ 1 1 0 ]      row 0 = patient 0
           [ ptr1 ] ----> [ 1 0 0 ]      row 1 = patient 1
           [ ptr2 ] ----> [ 0 1 1 ]      row 2 = patient 2
```

`adj[i][j]` means: take row pointer number *i*, then element number *j* in that row. So `adj[1][0]` is the first number of the second row.

**The struct, field by field** (`graph.h`, frozen in Section F; I use it exactly):

```c
typedef struct {
    int   numPatients;       /* rows */
    int   numDonors;         /* columns */
    int   edgeCount;
    int  *patientIds;        /* length numPatients; row i  <-> store->patients.items[i] at build time */
    int  *donorIds;          /* length numDonors;   col j  <-> store->donors.items[j]   at build time */
    int **adj;               /* numPatients x numDonors, calloc'd; adj[i][j] is 0 or 1 */
    int  *patientDegree;     /* row sums */
    int  *donorDegree;       /* column sums */
    char  cityFilter[CITY_LEN];   /* "" when no filter */
} BipartiteGraph;
```

| Field | Meaning |
|---|---|
| `numPatients` | Number of rows = number of patients |
| `numDonors` | Number of columns = number of donors |
| `edgeCount` | Number of 1s in the matrix |
| `patientIds` | Copy of patient ids; `patientIds[i]` is the id of row *i* |
| `donorIds` | Copy of donor ids; `donorIds[j]` is the id of column *j* |
| `adj` | The matrix (array of row pointers) |
| `patientDegree` | Row sums, one per patient |
| `donorDegree` | Column sums, one per donor |
| `cityFilter` | The filter text that was applied ("" = none) |

**How one row/column maps to one record.** Row *i* is `store->patients.items[i]` and column *j* is `store->donors.items[j]`, at the moment the graph was built. The ids are copied so the JSON can print real ids. This only stays correct while the store is not changed, which is true inside one request (the graph is thrown away at the end).

**Worked example (3 x 3, assuming 4-byte int and 8-byte pointer).** One `calloc` for 3 pointers (24 bytes), then three `calloc`s of 3 ints (12 bytes each). Total about 60 bytes plus the allocator's own overhead. For the original sample data (8 x 12): 96 ints = 384 bytes. For the enlarged data (120 x 200): 24,000 ints = 96,000 bytes, about 94 KB (calculation, not measured).

**Pseudocode.**
```
if numPatients > 0 and numDonors > 0:
    adj = calloc(numPatients pointers)             -> if NULL: fail
    for each row i: adj[i] = calloc(numDonors ints) -> if NULL: fail
fail: free every row already made, then the pointer array; leave graph empty; return NOMEM
```

**Real code excerpt** (`graph_build`):
```c
if (n > 0 && m > 0) {
    g->adj = calloc((size_t)n, sizeof(int *));
    if (g->adj == NULL) {
        goto fail;
    }
    for (i = 0; i < n; i++) {
        g->adj[i] = calloc((size_t)m, sizeof(int));
        if (g->adj[i] == NULL) {
            goto fail;
        }
    }
```

**Why `calloc`, not `malloc`?** `calloc` fills memory with zeros. Zero means "no edge", so I only have to write the 1s. Also `calloc(count, size)` checks `count * size` for overflow by itself, which the project rules ask us to guard.

**Why no `malloc(0)`?** If either side has zero records, there is no table to make. `malloc(0)` is allowed to return NULL *or* a special pointer, and NULL would look like "out of memory". So in that case `adj`, `patientDegree` and `donorDegree` stay NULL, and the code treats NULL as "all zeros" (`int_at`, `graph_has_edge`).

**Cost.** Memory: n x m numbers + n pointers + 2 id arrays + 2 degree arrays. Time to allocate: n + 5 `calloc` calls.

**Why this approach / alternative.** A matrix gives instant "is there an edge?" checks and trivial row/column sums, and the graph is dense (expected about 43% of cells are 1 with the enlarged data: 10,339 / 24,000; this is an *expected* value). *Alternative:* one big block of n x m ints (a single `calloc` and index `i*m + j`). It is faster to allocate, but `adj` is `int **` in the frozen header, so I kept row pointers. Another alternative: `unsigned char` or bits instead of `int` (4x to 32x less memory); not done because the header is frozen and `int` is simplest.

### 4.3 Degrees and the handshake property

**Idea in plain English.** The *degree* of a dot is the number of lines touching it.
- degree(patient *i*) = **sum of row *i*** = how many donors could help patient *i* (their "choices").
- degree(donor *j*) = **sum of column *j*** = how many patients donor *j* could serve.

**Worked example** (the 3 x 3 matrix above): row sums 2, 1, 2; column sums 2, 2, 1. Add the row sums: 2+1+2 = **5**. Add the column sums: 2+2+1 = **5**. And `edgeCount` is **5**.

**Handshake property.** Every edge has exactly one end on the patient side and one on the donor side. If you count line-ends on the left you get E; if you count line-ends on the right you also get E. So **sum of patient degrees = sum of donor degrees = edgeCount**. It always holds, with or without a city filter. In the team's real run with the original sample data, the matrix showed 8 rows x 12 columns, and the row sums and column sums both added to 29, the same as the 29 edges in `/api/stats` (reported by the team's curl check; I did not run it myself).

**Why a donor can have degree 0:** (1) the donor is unavailable, (2) the donor is in another city than the filter, or (3) no patient's blood group can receive from that donor's blood group. A patient has degree 0 when no available donor (in that city) is compatible.

**Pseudocode.**
```
patientDegree[i] = 0 for all i;  donorDegree[j] = 0 for all j
for i in 0..numPatients-1:
    for j in 0..numDonors-1:
        patientDegree[i] += adj[i][j]     # row i total
        donorDegree[j]   += adj[i][j]     # column j total
```

**Real code excerpt** (`graph_compute_degrees`):
```c
for (i = 0; i < g->numPatients; i++) {
    for (j = 0; j < g->numDonors; j++) {
        g->patientDegree[i] += g->adj[i][j];
        g->donorDegree[j]   += g->adj[i][j];
    }
}
```

**Cost.** Time: n x m additions (one pass over the matrix). Memory: n + m extra numbers.

**Why this approach / alternative.** One pass fills both arrays. *Alternative:* count edges while filling the matrix in `graph_build`. That is slightly faster, but a separate `graph_compute_degrees` function (required by the header) is clearer and can be re-run.

### 4.4 Design decision: rebuild from scratch on every request

**Idea.** Each call to `/api/graph`, `/api/graph/matrix` or `/api/graph/degrees` creates a new `BipartiteGraph`, uses it, and frees it before the handler returns. Nothing is stored between requests.

**Why:** the graph can **never be stale**. If a donor registers or becomes unavailable, the next request simply sees the new data. There is no "update the matrix" code that could contain a bug.

**Trade-off (honest):** simple and always correct, but it repeats work. Every request does about patients x donors checks again, and allocates the same amount of memory again.

**Worked example.** Original data: 8 x 12 = 96 checks per request. Enlarged data: 120 x 200 = 24,000 checks per request. I have **not measured** the time on the real app (**VERIFY** by clicking the graph page and timing it, if asked).

**Pseudocode.**
```
handler:  graph_init -> read city -> graph_build -> write JSON -> graph_free   (always)
```

**Real code excerpt** (`api_graph.c`, inside `handle_graph_request`):
```c
st = graph_build(&g, &app->store, city);
if (st != STATUS_OK) {
    http_send_error(res, st, NULL);   /* NULL -> default message for st */
    goto cleanup;
}
http_begin_ok(res, 200);
/* ... switch picks graph_write_json / graph_write_matrix_json / graph_write_degrees_json ... */
http_end_ok(res);

cleanup:
    graph_free(&g);
```

**Alternative:** keep one graph inside `AppState` and update it whenever a record is added or changed. Faster for repeated requests, but every `records_*` function that changes data would have to invalidate it. Forgetting one place gives a wrong graph. For a small in-memory project, correctness wins.

### 4.5 Writing the graph as JSON (row-major edge list)

**Idea.** Turn the matrix into text the browser can read. "Row-major order" means: go through row 0 left to right, then row 1, and so on.

**Worked example.** For the 3 x 3 matrix the edge list is, in this order: (patient 1, donor 101), (1, 102), (2, 101), (3, 102), (3, 103).

**The three formats (exact fields):**

- `GET /api/graph` (`graph_write_json`):
  `cityFilter`, `numPatients`, `numDonors`, `edgeCount`, `patients` [`id`, `name`, `bloodGroup`, `city`, `degree`], `donors` [`id`, `name`, `bloodGroup`, `city`, `available` (true/false), `degree`], `edges` [`patientId`, `donorId`].
- `GET /api/graph/matrix` (`graph_write_matrix_json`):
  `cityFilter`, `rows`, `cols`, `patientIds`, `donorIds`, `matrix`, `rowSums`, `columnSums`. For the 3 x 3 example it printed (my test, stub data):
  `{"cityFilter":"","rows":3,"cols":3,"patientIds":[1,2,3],"donorIds":[101,102,103],"matrix":[[1,1,0],[1,0,0],[0,1,1]],"rowSums":[2,1,2],"columnSums":[2,2,1]}`
- `GET /api/graph/degrees` (`graph_write_degrees_json`):
  `cityFilter`, `patients` [`id`, `name`, `degree`], `donors` [`id`, `name`, `degree`], `edgeCount`, `patientDegreeSum`, `donorDegreeSum`.

All three are wrapped by Dev 1's `http_begin_ok` / `http_end_ok` into `{"ok":true,"data": ... }`.

**Real code excerpt** (`graph_write_json`, edge list):
```c
sb_append(sb, "],\"edges\":[");
for (i = 0; i < g->numPatients; i++) {
    for (j = 0; j < g->numDonors; j++) {
        if (graph_has_edge(g, i, j)) {
            if (!firstEdge) {
                sb_append_char(sb, ',');
            }
            firstEdge = 0;
            sb_appendf(sb, "{\"patientId\":%d,\"donorId\":%d}",
                       int_at(g->patientIds, i), int_at(g->donorIds, j));
        }
    }
}
```

**Size warning with the enlarged sample data** (200 donors, 120 patients; **expected**, not measured: about 10,339 edges). One edge entry is about 30-32 characters, so the unfiltered `/api/graph` answer is roughly 300-350 KB of text (my estimate; **VERIFY** with `curl.exe -s ... -o graph.json` and look at the file size). The browser has to draw all those lines, which is heavy. A city filter keeps all vertices but only about one city's donors have lines: roughly 2,000 edges (rough arithmetic: 10,339 split over five cities is about 2,068; the exact per-city numbers depend on the data; **VERIFY**). The matrix JSON is 24,000 small numbers, roughly 50 KB.

**Cost.** Time: n x m to scan the matrix, plus work proportional to the number of edges for the output. Memory: the JSON text itself (`StrBuf`, Dev 2's growable string).

**Why this approach / alternative.** Scanning the matrix in row-major order gives a predictable order that tests can compare exactly. *Alternative:* send only the matrix and let JavaScript find the edges. Rejected: the rule is that JavaScript only displays; and an explicit edge list is easier to draw.

## 5. Memory and pointers in my part

**Allocations I make (all with `calloc`, all in `graph_build` / `graph_compute_degrees`):**

| What | Call | Owned by | Freed by |
|---|---|---|---|
| `patientIds` (n ints) | `calloc(n, sizeof(int))` | the `BipartiteGraph` | `graph_free` |
| `donorIds` (m ints) | `calloc(m, sizeof(int))` | the `BipartiteGraph` | `graph_free` |
| `adj` (n row pointers) | `calloc(n, sizeof(int *))` | the `BipartiteGraph` | `graph_free` (after the rows) |
| `adj[i]` (m ints each) | `calloc(m, sizeof(int))` | the `BipartiteGraph` | `graph_free` |
| `patientDegree`, `donorDegree` | `calloc(...)` | the `BipartiteGraph` | `graph_free` (or the next `graph_compute_degrees`) |

I never use `malloc` or `realloc`. For a graph with both sides non-empty that is n + 5 `calloc` calls.

**Who owns what.** The `RecordStore` belongs to `main()` and I only *read* it. The `BipartiteGraph` is a **local variable** of the handler: init -> use -> free before the handler returns. The graph is valid only while the store is not modified.

**What happens if an allocation fails.** Every `calloc` result is checked. On failure the code does `goto fail`, which calls `graph_free`. Because the row-pointer array was made by `calloc`, rows not yet allocated are NULL, and `free(NULL)` does nothing, so the rows already made are freed, then the pointer array, then everything else. The graph is left empty and `graph_build` returns `STATUS_ERR_NOMEM` (the handler turns that into HTTP 500).

**How double free and leaks are avoided.**
```c
void graph_free(BipartiteGraph *g)
{
    int i;
    if (g == NULL) { return; }
    if (g->adj != NULL) {
        for (i = 0; i < g->numPatients; i++) { free(g->adj[i]); }
        free(g->adj);
    }
    free(g->patientIds);
    free(g->donorIds);
    free(g->patientDegree);
    free(g->donorDegree);
    graph_init(g);        /* everything back to NULL / 0 */
}
```
After freeing, `graph_init` sets every pointer to NULL. A second `graph_free` then sees NULL pointers and does nothing, so double free is impossible. `graph_build` calls `graph_free` first, so rebuilding never leaks. The handler has a single `cleanup:` label, so every path (success or error) frees the graph.

**One common beginner mistake.** Freeing `g->adj` *before* freeing the rows. Then the row pointers are lost and every row leaks (or you read freed memory). The right order is rows first, then the array of row pointers. A second classic mistake: writing `calloc(n, sizeof(int))` for the row-pointer array. It must be `sizeof(int *)`, because it holds pointers.

## 6. Validation and error handling in my part

| Situation | What happens | Code | HTTP |
|---|---|---|---|
| `?city=` missing or empty | No filter (all donors count) | OK | 200 |
| `?city=` malformed or longer than 29 characters (`CITY_LEN - 1`) | Rejected, nothing is truncated silently | `BAD_REQUEST` | 400 |
| Out of memory while building | Graph left empty, error returned | `OUT_OF_MEMORY` | 500 |
| `graph_build` gets NULL store or edge count would overflow `int` | Error returned | `INTERNAL_ERROR` | 500 |
| Handler called with NULL `app` or `req` | Error returned | `INTERNAL_ERROR` | 500 |
| JSON buffer ran out of memory while writing | Dev 1's `http_end_ok` replaces the body with a 500 error | `OUT_OF_MEMORY` | 500 |
| Wrong method (e.g. POST `/api/graph`) | Not my code: the router answers | `METHOD_NOT_ALLOWED` | 405 |

Error body format: `{"ok":false,"error":{"code":"BAD_REQUEST","message":"Query parameter 'city' is malformed or longer than 29 characters"}}`.

There is no 404 on my endpoints: an empty graph is a normal answer (200 with empty arrays), never an error.

What I do **not** validate: the text of the city (no trimming, so `Pune ` with a trailing space matches nothing). Matching is case-insensitive, done by Dev 2's `compat_city_matches`.

## 7. How I coordinated with the other developers

**The way we worked.** Six Claude accounts: one Orchestrator and five Developers. We never talked directly. The human team member carried messages. All coordination went through **one binding written specification** (the Common Technical Specification) with frozen headers, JSON formats, business rules, the status/HTTP table and memory-ownership rules. If a Developer wanted a header changed, he had to write a "PROPOSED SPEC CHANGE" instead of editing it.

**Contracts I relied on:**
- `compat_is_edge` is *the* edge rule (Dev 2). I never re-implemented it.
- `StrBuf` and `sb_*` (Dev 2): if an allocation fails, `failed` becomes 1 and later appends do nothing, so I do not have to check after each append.
- `http_query_get`, `http_begin_ok`, `http_end_ok`, `http_send_error` (Dev 1) and the `HttpRequest` / `HttpResponse` types.
- `RecordStore` arrays can be read directly (`items[i]`, `count`), and the store does not change within one request.
- The JSON shapes of Section H and the status table of Section I.

**What others rely on from me:**
- Dev 4's `matching_compute(const BipartiteGraph *g, ...)` reads `g->adj`, `numPatients`, `numDonors`, and never recomputes compatibility. **Rows = patients, columns = donors** is the contract.

## 9. Limitations and known risks

- **Repeated work.** Every request rebuilds the graph: patients x donors checks each time. Fine for 12 x 8 and (expected) fine for 200 x 120, but I have not timed it and it would not scale to very large data.
- **Big output with the enlarged data.** Unfiltered `/api/graph` is roughly 10,000 edges (expected, about 300-350 KB by my estimate), and drawing them all in the browser is heavy. The city filter helps.
- **Memory use.** `int` per cell is wasteful (a `char` or one bit would do), and the header is frozen, so I did not change it.
- **Matrix, not adjacency list.** Good for dense graphs; wasteful for very sparse ones.
- **The graph is only valid while the store is unchanged.** I rely on the server handling one request at a time (the spec says `server_run` is a blocking loop). If the server ever became multi-threaded, a lock would be needed.
- **City filter is an exact (case-insensitive) match** with no trimming. A filter with a trailing space finds nothing.
- **The filter is capped at 29 characters.** The API rejects longer ones (400). If `graph_build` itself is called with a longer filter, it truncates safely, so the stored filter is the truncated one.
- **Tests use stubs.** They prove the graph logic, not the blood-group table or the real JSON helpers. They use file-level counters and a global stub table (needed because a stub function cannot receive extra arguments); this is test code only.
- **Not verified:** Windows build of my files in isolation, real-server demo, browser test, enlarged-data numbers (see section 8).
- **Matrix shape for one-side-empty graphs** (`[[]]`) is my own choice; the spec only said "may be 0".

## 11. VIVA Q&A

### Questions about my part

**Q1. What is a bipartite graph?**
A graph whose vertices split into two groups, and every edge joins one vertex from each group. In our project the groups are patients and donors, so there is never an edge between two patients or two donors.

**Q2. What are the vertices and edges in your graph?**
Vertices are all patients (P) and all donors (D). An edge joins patient *i* and donor *j* when `compat_is_edge` returns 1: the blood group is compatible, the donor is available, and the city matches the filter.

**Q3. Why do all patients stay in the graph when a city filter is used?**
The filter looks at the *donor's* city, so it only removes lines, not vertices. A patient with no lines stays with degree 0, which tells the user that no donor was found there.

**Q4. What is an adjacency matrix and what do rows and columns mean here?**
It is a table of 0s and 1s. Row *i* is patient *i*, column *j* is donor *j*, and `adj[i][j]` is 1 if there is an edge. It is n x m, not necessarily square.

**Q5. Why is `adj` an `int **`?**
The size is only known at run time and the project forbids fixed limits. So I allocate an array of row pointers, then one row of ints per pointer. `adj[i][j]` means "row pointer *i*, element *j*".

**Q6. Why `calloc` and not `malloc`?**
`calloc` fills the memory with zeros, and zero means "no edge", so I only write the 1s. It also checks `count * size` for overflow.

**Q7. What happens if a row allocation fails halfway?**
I jump to the `fail` label, which calls `graph_free`. It frees the rows already created, then the row-pointer array, and everything else. The graph is left empty and `graph_build` returns the out-of-memory status, which becomes HTTP 500.

**Q8. Why do you never call `malloc(0)`?**
Its result is implementation-defined: it may be NULL or a unique pointer, and NULL looks like a failure. So when there are zero patients or zero donors I keep the pointers NULL, and my code reads NULL arrays as "all zeros".

**Q9. How do you compute degrees?**
Two nested loops over the matrix. Each `adj[i][j]` is added to `patientDegree[i]` (row sum) and `donorDegree[j]` (column sum).

**Q10. What does a degree mean in this project, and why can a donor have degree 0?**
Patient degree = how many donors could help that patient. Donor degree = how many patients the donor could serve. A donor has degree 0 if unavailable, in another city than the filter, or no patient group can receive from that blood group.

**Q11. What is the handshake property?**
The sum of all patient degrees equals the sum of all donor degrees, and both equal the number of edges, because every edge has exactly one end on each side. In the team's run with the original sample data both sums were 29.

**Q12. Why do you rebuild the graph on every request?**
So it can never be stale after a registration or an availability change. The price is repeated work of about patients x donors checks. For a small in-memory project, being always correct is more valuable.

**Q13. What does `graph_free` do and why is it safe to call twice?**
It frees the rows, the row array, the id arrays and the degree arrays, then calls `graph_init`, which sets all pointers to NULL. A second call finds only NULL pointers and `free(NULL)` does nothing.

**Q14. In what order are the edges in the JSON?**
Row-major: patient row 0 from left to right, then row 1, and so on. For the 3 x 3 example: (1,101), (1,102), (2,101), (3,102), (3,103).

**Q15. How do you read the optional `?city=` parameter?**
With `http_query_get`. If it is missing or empty there is no filter. If it is malformed or longer than 29 characters, the handler answers `BAD_REQUEST` (HTTP 400). Otherwise the text is passed to `graph_build` and stored in `cityFilter`.

**Q16. What is the time and memory cost of building the graph?**
Time is about patients x donors calls to `compat_is_edge`. Memory is the same amount of ints plus small arrays. For 120 x 200 that is 24,000 cells, about 94 KB if an int is 4 bytes (a calculation, not a measurement).

### Three tricky questions

**T1. "Your matrix is 8 x 12. Is that the adjacency matrix of the graph?"**
*Trap:* in strict graph theory, the adjacency matrix of a graph with P+D vertices is (P+D) x (P+D) and symmetric. Answer: "Strictly, what I store is the *biadjacency* matrix of the bipartite graph: it only records patient-to-donor edges, because the other two blocks (patient-patient, donor-donor) would be all zeros. It is rectangular, not symmetric, and that is enough for degrees and matching." Do not say "it is symmetric".

**T2. "With a city filter, the other cities' donors have degree 0. Doesn't that break the handshake property? Are they removed from the graph?"**
*Trap:* thinking the filter deletes vertices or changes the rule. Answer: "No. The filter removes edges only; every patient and donor stays as a vertex. The handshake property counts edges from both sides, so it always holds: both sums equal the new, smaller edge count. Donors outside the city simply contribute degree 0."

**T3. "A patient has degree 5 and another has degree 1. So the first patient will surely get a donor and the second maybe not?"**
*Trap:* confusing degree with matching. Answer: "Degree only says how many *choices* a patient has. Whether the patient gets a donor depends on competition: if those 5 donors are all wanted by other patients, nobody may be left. And a patient with degree 1 can still be matched if that donor is free. Choosing the best set of pairs is the matching algorithm, which belongs to Dev 4 (Kuhn's algorithm with augmenting paths)."

## 12. Glossary

1. **Vertex** - one dot of the graph; here, one patient or one donor.
2. **Edge** - a line between two vertices; here, "this donor can help this patient".
3. **Bipartite graph** - a graph whose vertices are in two groups, with edges only between the groups.
4. **Adjacency matrix** - a table of 0s and 1s where a 1 at row *i*, column *j* means an edge (in our case a rectangular patient-by-donor table).
5. **Degree** - the number of edges touching a vertex; for a patient it is the sum of their row, for a donor the sum of their column.
6. **Handshake property** - in a bipartite graph the sum of degrees on one side equals the sum on the other side, and both equal the number of edges.
7. **`calloc`** - C function that reserves memory and fills it with zeros, taking the count and the size of each item.
8. **`int **` (pointer to pointer)** - here, a pointer to an array of row pointers, each pointing to one row of ints.
9. **Row-major order** - going through a table row by row, each row from left to right.
10. **City filter** - the optional `?city=` text; only donors whose city matches (ignoring upper/lower case) can have edges.
