## 1. The 30-second summary

When a patient needs blood, the search page shows *all* compatible donors. But if **many** patients need blood **at the
same time**, two patients may want the same donor, and one donor can only give to one patient. My part solves this
"sharing" problem. It finds the **largest possible set of patient-donor pairs** where nobody shares a donor. It uses
**Kuhn's algorithm**, which is a recursive search for "augmenting paths". It also produces the numbers on the statistics
panel (`/api/stats`) and the demo data used to show everything working. The project needs it because it is the
graph-theory heart of the title: *a graph theory based search and matching system*.

## 4. Algorithms and key ideas

### 4.1 The problem in plain English (go deep)

**Analogy: chairs and guests.** Each patient is a guest. Each donor is a chair. A guest will only sit on certain chairs
(the compatible, available donors). Two guests cannot share one chair. We want to seat **as many guests as possible**.

* A **bipartite graph** has two groups (patients, donors); lines only go *between* the groups. A line means
  "this donor can give to this patient right now" (compatible blood group AND donor available AND city matches the
  optional filter - one function, `compat_is_edge`, by Dev 2).
* A **matching** is a set of lines where **no patient and no donor appears twice**.
* A **maximum matching** is a matching with the **most lines possible**. (Not the same as "a matching where you can't
  add another line": that can still be smaller than the maximum.)

**The greedy trap, with the course example.** Three patients, three donors:

```
          D1  D2  D3
    P1  [  1   1   0 ]    P1 can use D1 or D2
    P2  [  1   0   0 ]    P2 can use only D1
    P3  [  0   1   1 ]    P3 can use D2 or D3
```

*Greedy = "give each patient the first free donor".*

| Patient | Greedy picks | Result |
|---|---|---|
| P1 | D1 (first free) | P1-D1 |
| P2 | wants only D1, already taken | **stuck, no donor** |
| P3 | D2 (first free) | P3-D2 |

Greedy gives **2 pairs**. But **3** are possible: P1-D2, P2-D1, P3-D3. To get there, P1 must be **asked to move**
after it already has a donor. Greedy never reconsiders; Kuhn's algorithm does.

*(my sandbox)* The same thing happens on the real demo data: a "first free donor" rule gives 6 pairs, Kuhn gives 7.
I counted greedy with a small throwaway program using stand-in modules, so **VERIFY** if you quote the number 6.

### 4.2 Kuhn's algorithm (go deep)

**Idea in plain English.** Go through the patients one at a time. For the current patient, look at each donor they can
use. If the donor is free, take it. If the donor already belongs to someone else, **politely ask that person to move**
to another donor (and they may ask the next person, and so on). If the chain of moves works, everybody shifts and the
current patient gets a donor. That chain is an **augmenting path**.

**Augmenting path (plain English):** a chain that starts at a patient with no donor, goes to a donor who belongs to
someone, then to that someone's other donor, and so on, until it reaches a **free** donor. Moving everyone along the
chain gives **one more pair** than before.

Example from the 3x3 grid, while P1-D1 is already matched and P2 arrives:
`P2 -> D1 (belongs to P1) -> P1 -> D2 (free)`. After shifting: P2-D1 and P1-D2. We went from 1 pair to 2.

**Pseudocode** (matches `matching.c`):

```
for each patient u:                      # rows 0..numPatients-1
    clear visited[] (one flag per donor)
    if try_augment(u): matchCount++

try_augment(u):
    for each donor v with adj[u][v] == 1 and not visited[v]:
        visited[v] = 1
        if donorMatch[v] == -1 OR try_augment(donorMatch[v]):
            donorMatch[v] = u
            patientMatch[u] = v
            return 1
    return 0
```

**Real code (comments trimmed), `backend/matching.c`:**

```c
static int try_augment(const BipartiteGraph *g, MatchingResult *m, char *visited, int u)
{
    int v;

    for (v = 0; v < g->numDonors; v++) {
        if (g->adj[u][v] != 1 || visited[v]) {
            continue;
        }
        visited[v] = 1;
        if (m->donorMatch[v] == -1 || try_augment(g, m, visited, m->donorMatch[v])) {
            m->donorMatch[v] = u;
            m->patientMatch[u] = v;
            return 1;
        }
    }
    return 0;
}
```

**The main loop (comments trimmed):**

```c
for (u = 0; u < g->numPatients; u++) {
    memset(visited, 0, (size_t)g->numDonors);
    if (try_augment(g, m, visited, u)) {
        m->matchCount++;
    }
}
```

**Step-by-step trace of the 3x3 example.** (Names are 1-based here; in the C arrays P1 is index 0, D1 is index 0.)

| After | What happened | `patientMatch` (P1, P2, P3) | `donorMatch` (D1, D2, D3) | `matchCount` |
|---|---|---|---|---|
| start | nobody matched | -, -, - | -, -, - | 0 |
| **P1** | D1 is free, P1 takes D1 | D1, -, - | P1, -, - | 1 |
| **P2** | D1 is P1's. Ask P1 to move: P1 takes free D2. Then P2 takes D1. | D2, D1, - | P2, P1, - | 2 |
| **P3** | D1: no edge. D2 is P1's: ask P1 -> P1 tries D1 (P2's) -> ask P2 -> P2 has nothing else -> **fail**; P1 has nothing else -> **fail**. So D2 cannot be freed. Next donor D3 is free: P3 takes D3. | D2, D1, D3 | P2, P1, P3 | 3 |

In the C arrays the final answer is `patientMatch = {1, 0, 2}` and `donorMatch = {1, 0, 2}` (checked by `test_augmenting_path`).
Notice **P3's step contains a failed branch**: the program asked two people to move, it did not work, and it simply
tried the next donor. Nothing was changed by the failed branch. That is also why `visited[]` matters.

**Why `visited[]` is cleared for each new patient but NOT inside the recursion.**

* *Inside one search* we must **not** clear it. `visited[]` is the notebook that says "I already asked about this donor
  during this search". If we cleared it inside the recursion, two patients could keep asking each other forever, or we
  would explore the same donors again and again.
* *Between two searches* we **must** clear it. After a search, the matching has changed. A donor who was a dead end
  a moment ago might be useful now. A new patient needs a clean notebook.

**Why the recursion always ends.** Each recursive call happens because a **new donor was just marked visited**. A donor
can be marked only once per search, so there are at most (number of donors) calls. Also, each call is for a **different
patient** (the current owner of that new donor, and each patient owns at most one donor). So the depth is at most the
number of patients, and also at most the number of donors. A finite number of steps - it ends.
Recursion (a function that calls itself on a smaller problem, with a stopping rule) is a required topic of the course,
and this is a real use of it.

**Informal reason the result is maximum.** (1) Every augmenting path we flip gives **exactly one more** pair, because
the chain has one more "new" line than "old" lines. (2) A known result (Berge's theorem - **VERIFY** whether your
course expects the name) says: *if no augmenting path exists, the matching cannot be improved.* (3) We try to find an
augmenting path for every patient. If none exists for a patient, that patient stays unmatched.
Extra evidence: `test_matching.c` compares Kuhn with a brute-force search on 300 random small graphs *(my sandbox)*.

**Cost in simple terms.**

* *Time, textbook version:* about **patients x edges**. Each of the P searches may touch every edge once.
* *Time, my version:* I scan a **matrix row** (D cells) in each recursive call, and one search makes at most D+1 calls,
  so the worst case is about **patients x donors x donors**. Example upper bound for the enlarged data:
  120 x 201 x 200 = 4,824,000 cell checks. This is a **worst-case bound**, not a measurement.
* *Memory:* two index arrays (`patientMatch`: P ints, `donorMatch`: D ints) and one `visited` array (D bytes), besides
  the matrix that Dev 3 owns.

**Why this approach, and an alternative.** Kuhn's algorithm is short, uses only recursion and arrays, and a beginner can
trace it by hand. An alternative is **Hopcroft-Karp** (faster for large graphs, but longer and harder to explain), or
a **max-flow** method (more general, more code). For 120 patients and 200 donors, speed is not a problem.

### 4.3 Data structures and how results are written

```c
typedef struct {
    int  numPatients;
    int  numDonors;
    int  matchCount;
    int *patientMatch;   /* length numPatients: matched donor COLUMN or -1 */
    int *donorMatch;     /* length numDonors:   matched patient ROW or -1 */
} MatchingResult;
```

* **`patientMatch[u]`** = which donor *column* patient row `u` has, or `-1`. **`donorMatch[v]`** = which patient *row*
  donor column `v` has, or `-1`. They always agree with each other (the tests check this).
* **Why indexes, not ids?** Inside the algorithm we compare small numbers 0, 1, 2... and use them directly as array
  positions; that is fast and simple. Ids like 101 or 102 would need a search every time. We translate to ids and names
  **only when writing JSON**: row `i` of the graph is `store->patients.items[i]` and column `j` is
  `store->donors.items[j]`.
* **Unmatched lists.** `unmatchedPatients` = rows where `patientMatch[row] == -1`. `unmatchedDonors` = columns where
  `donorMatch[col] == -1`. This includes donors with **degree 0** (nobody can use them: for example an unavailable donor
  or an AB+ donor when there is no AB+ patient), and also available donors who were simply not needed.
  (*Assumption I made:* the spec's note "donors with degree 0 ... are unmatched" does not say that *other* unused donors are
  listed too. I list every donor without a partner. **VERIFY** this matches what Dev 5's page expects.)
* **Empty graphs and unequal sizes.** If there are 0 patients or 0 donors, `matching_compute` returns `STATUS_OK` with
  `matchCount = 0` and **both arrays `NULL`** (never `malloc(0)`), but still stores the correct `numPatients` and
  `numDonors`:

```c
if (g->numPatients == 0 || g->numDonors == 0) {
    return STATUS_OK;
}
```

  The JSON writer treats `NULL` arrays as "nobody matched". With **more patients than donors**, the extra patients stay
  unmatched; with **more donors than patients**, the extra donors stay unmatched. Both cases are tests.

## 5. Memory and pointers in my part

**What I allocate.**

| Where | Call | Freed by |
|---|---|---|
| `matching_compute` | `malloc` for `patientMatch` (P ints) and `donorMatch` (D ints) | `matching_free` (called by the handler) |
| `matching_compute` | `calloc` for `visited` (D bytes) | `free(visited)` before `matching_compute` returns |
| `api_*` handlers | none directly; `BipartiteGraph graph` and `MatchingResult matching` are **local variables**; their arrays live on the heap | `graph_free(&graph)` and `matching_free(&matching)` in the single `cleanup:` block |
| `read_city_filter` | `JsonObject` allocated inside `json_parse_object` (Dev 2) | `json_object_free(&obj)` in its `cleanup:` block |

I use **no** `realloc`.

**Who owns what.** The graph and the matching result are **local to the request**: init -> use -> free. The
`RecordStore` belongs to `main()` (Dev 1). A matching result is only valid while the store is not changed, because
row/column numbers refer to the store's array positions.

**If an allocation fails.** Allocation failure sets `st = STATUS_ERR_NOMEM`, the result is wiped with `matching_free`
(so it is empty, never half-filled), `matching_compute` returns the error, and the handler calls
`http_send_error(res, st, NULL)`. Per the status table that is **HTTP 500, code `OUT_OF_MEMORY`**. The failure path was
**not** tested with a forced failure *(VERIFY if you want to claim it)*.

**Avoiding double free and leaks.**

* `matching_free` calls `free()` on both arrays (freeing `NULL` is allowed) and then calls `matching_init`, which sets
  both pointers to `NULL`. A second `matching_free` therefore frees `NULL` - harmless. `test_recompute_and_double_free`
  checks this.
* `matching_compute` calls `matching_free(m)` first, so computing twice into the same result does not leak the old arrays.
* Each handler has **one** `cleanup:` label at the end, and every error path does `goto cleanup`.
* The `visited` array is never handed to the caller, so it cannot be freed twice or forgotten.

```c
static Status alloc_int_array_filled_with_minus_one(int n, int **out)
{
    int *array;
    int i;

    *out = NULL;
    if (n <= 0) {
        return STATUS_ERR_INTERNAL;
    }
    if ((size_t)n > SIZE_MAX / sizeof(int)) {
        return STATUS_ERR_NOMEM;
    }
    array = (int *)malloc((size_t)n * sizeof(int));
```

**A common beginner mistake (and how it applies here).** Calling `matching_free` on a `MatchingResult` that was never
initialised: its pointers contain random garbage, and `free(garbage)` crashes. That is why each handler calls
`matching_init(&matching)` **first**, before anything else can `goto cleanup`.
A second mistake: `malloc(0)` when a side is empty. I avoid it by returning early.

## 9. Limitations and known risks

* **Recursion depth** is at most the number of patients (and donors). Fine for 120 / 200; with hundreds of thousands the
  C stack could overflow. The spec required a recursive version.
* **Cost** is about patients x donors x donors in my matrix version. Fine here; a list-based version would scale better.
* **No preference rules.** All compatible donors are treated as equal: no "nearest donor", no "rarest blood group first".
  The matching only maximises the **count**.
* **The matching is not unique.** A different record order can give different pairs but the same number of pairs.
* **Unmatched means "no available compatible donor under our rules"**, not "medically refused". The system gives potential
  compatibility only; it is not medical approval.
* **Snapshot only.** The matching is recomputed on every request; a result becomes invalid when records change.
* **`/api/matching` lists only pairs**, so the frontend needs a second request (`/api/graph`) to draw all edges.
* **The enlarged data hides the teaching scenarios** (section 4.5).
* **`{"city":null}` returns 400** (a design choice; a more forgiving server could treat it as "no filter").
* **Tests use stand-ins** for other modules and were run only on my Linux sandbox. The enlarged-data results are expected,
  not measured. I have not seen the enlarged `sample_data.c`.

## 11. VIVA Q&A

### 11.1 Twelve questions about my part (plus a few extra)

**1. What is a matching?** A set of patient-donor pairs where no patient and no donor appears twice. In our case, each
patient gets at most one donor and each donor serves at most one patient.

**2. What does "maximum" matching mean?** The matching with the largest possible number of pairs. It is different from a
matching you cannot extend, which can still be smaller than the maximum.

**3. Why is "give each patient the first free donor" not enough?** It never changes earlier choices. With P1{D1,D2},
P2{D1}, P3{D2,D3} it gives 2 pairs, but 3 are possible if P1 moves to D2.

**4. What is an augmenting path?** A chain that starts at an unmatched patient and ends at a free donor, passing through
donors who already have a patient. Shifting everyone along the chain adds exactly one pair.

**5. Explain `try_augment` in words.** For patient `u`, look at each unvisited donor `u` can use and mark it visited. If the
donor is free, take it. If it belongs to another patient, ask that patient to find another donor (recursive call). If
they can, take the donor; if not, try the next one.

**6. Why do you clear `visited[]` for every new patient but not inside the recursion?** Inside one search it stops endless
loops and repeated work, so it must stay. Between searches the matching has changed, so earlier dead ends may now work and
we need a clean notebook.

**7. Why does the recursion always end?** Each recursive call comes from marking a new donor as visited, and a donor is
marked at most once per search. So there are at most as many calls as donors, and each call is for a different patient.

**8. Why is the result maximum?** Each augmenting path found adds exactly one pair, and a known theorem says that if no
augmenting path exists the matching cannot be improved. We try every patient. (Evidence: tests compared with brute force
on 300 random small graphs, in my sandbox.)

**9. What is the cost?** The textbook figure is about patients x edges. Mine scans a matrix row per call, so the worst
case is about patients x donors x donors. Memory is two index arrays and one `visited` array.

**10. What do `patientMatch` and `donorMatch` hold, and why indexes?** `patientMatch[row]` is the donor column or -1;
`donorMatch[col]` is the patient row or -1. Indexes are used directly as array positions, which is simple and fast; ids
and names are only looked up when writing JSON.

**11. How do you get the unmatched lists?** Unmatched patients are rows with `patientMatch == -1`; unmatched donors are
columns with `donorMatch == -1`. Donors with degree 0, including unavailable donors, are always in the second list.

**12. How do you handle empty graphs and different sizes, without `malloc(0)`?** If there are no patients or no donors,
`matching_compute` returns `STATUS_OK` with `matchCount` 0 and both arrays `NULL`. The JSON writer treats `NULL` as "nobody
matched". More patients than donors leaves patients unmatched; more donors than patients leaves donors unmatched.

**13. What does `POST /api/matching` accept and return?** An optional body `{"city":"Pune"}`; an empty body means no filter.
It returns `cityFilter`, `matchCount`, `numPatients`, `numDonors`, `pairs` (patientId, patientName, donorId, donorName),
`unmatchedPatients` and `unmatchedDonors`. Invalid JSON gives 400 `BAD_REQUEST`.

**14. What does `GET /api/stats` return and why unfiltered?** `donorCount`, `availableDonorCount`, `unavailableDonorCount`,
`patientCount`, `edgeCount`, `maxMatching`, `unmatchedPatientCount`. It uses no city filter because it describes the whole system.

**15. Why does the original data give 7 and not 8?** Patients 2 and 7 are both O- and each can use only donor 101, the
only available O- donor. Two patients share one possible donor, so at most one can be served. (Donor 107 is O- but unavailable.)

**16. How does the demo data show the augmenting path, and why does record order matter?** The O- donor 101 is first, so
patient 1 grabs it first. Patient 2 can use only 101, so patient 1 must move to 102. If 101 were last, no move would be needed.

**17. What happens if memory runs out?** The matching result is wiped, `matching_compute` returns `STATUS_ERR_NOMEM`, and the
handler returns HTTP 500 `OUT_OF_MEMORY`. I did not test this with a forced failure.

### 11.2 Three tricky questions

**T1. "You clear `visited[]` for every patient. Doesn't that make the algorithm exponential?"**
*Trap:* thinking that clearing means re-exploring everything for ever. *Answer:* No. Inside one search each donor is
visited at most once, so one search is bounded by the number of donors (times a row scan). Clearing happens only once per
patient, so the total stays polynomial: about patients x donors x donors in my version.

**T2. "On the enlarged data you get 120 of 120. Does that prove your algorithm is correct?"**
*Trap:* treating a good-looking result as a proof, and treating *expected* numbers as *measured*. *Answer:* No. First, the 120
is an expected value, not yet measured on the real app. Second, a full matching only shows that there are enough donors.
Correctness comes from the augmenting-path argument and from the test that compares Kuhn with brute force on random small graphs.

**T3. "`/api/stats` says maximum matching 120, but a request with city Pune gives 37. Which one is right?"**
*Trap:* thinking one of them is a bug. *Answer:* Both are right. They answer different questions. `/api/stats` uses the
unfiltered graph (the whole system). The Pune request removes every donor outside Pune before matching, so fewer pairs are
possible. (Again: these are expected values on the enlarged data.)

## 12. Glossary

* **Bipartite graph:** a graph with two groups (patients, donors) where lines only join the two groups.
* **Edge:** a line between a patient and a donor meaning "this donor can give to this patient right now".
* **Adjacency matrix:** a table of 0s and 1s, one row per patient and one column per donor.
* **Degree:** how many lines touch a patient (row sum) or a donor (column sum).
* **Matching:** a set of edges where no patient and no donor is used twice.
* **Maximum matching:** a matching with the greatest possible number of edges.
* **Augmenting path:** a chain from an unmatched patient to a free donor through already-matched donors; shifting along it adds one pair.
* **Recursion:** a function that calls itself on a smaller part of the problem, with a rule to stop.
* **`visited[]`:** a notebook with one flag per donor, saying "already tried during this search".
* **`-1` in `patientMatch`/`donorMatch`:** the marker for "nobody matched yet".
